# agent/COLLABORATION · 多 agent 协同协议

> 适用场景：一个任务拆给多个 agent **并行**推进（如"前端渲染重构 + 引擎算法调整 + 测试补强"
> 同时进行）。串行接力见 [RELAY.md](RELAY.md)。
> 目标：**没有 agent 需要全量阅读项目**，也没有两个 agent 改同一文件。

## 角色

| 角色 | 职责 |
|---|---|
| 主控 agent | 拆任务、发任务卡、拥有共享契约（API 形状 / `labels.js` / D1 schema / 限额）、验收合并 |
| 执行 agent | 只领一张任务卡，只改卡上列出的文件，按卡验收 |
| 评审 agent | 只读 diff 与任务卡，不改代码，输出通过/打回 |

单人会话时主控与执行由同一 agent 扮演，协议不变。

## 铁律

1. **文件 Ownership**：同一文件在同一时间只允许一个 agent 修改。任务卡上的"拥有文件"
   清单即写锁；需要动别人的文件 = 先找主控换卡，不允许私下改。
2. **共享契约集中变更**：API JSON 形状、D1 列语义、`labels.js` 中文单源、限额双路行为，
   只能由主控 agent 改，且必须同步通知所有相关执行 agent。
3. **任务卡先行**：动手前从 [templates/task-card.md](templates/task-card.md) 复制填写，
   写明目标 / 拥有文件 / 明确不做 / 验收标准。没有卡不动手。
4. **最小阅读**：执行 agent 按根 [AGENTS.md](../../AGENTS.md) 的「按任务类型取读」表读文档，
   只读任务涉及的源码。禁止"先通读一遍项目"。
5. **分支隔离**：每个任务一个分支（`feat/<任务名>` / `fix/<任务名>` / `docs/<任务名>`），
   从最新 `main` 切出；合并回 `main` 由主控执行。
6. **提交规范**：conventional commits；一次提交只含本任务文件；不 force push `main`。
7. **禁止事项**：不提交密钥；不动 `_research_raw/`；不改写已发布历史；不借验证之名扩任务；
   未验证的事项如实说明。

## 标准流程

```
主控：拆任务 → 写任务卡（每卡 ≤ 1 个可验收目标）→ 建分支 → 派发
执行：读卡 → 按需读 L1/L2 文档 → 只改卡内文件 → 自测（卡内验收标准）→ 提交 → 汇报
主控：收集 diff → 指派评审 agent（可选）→ 合并 → 更新 MEMORY.md
```

## 并行任务拆分原则

- 按**文件 Ownership** 切，不按"模块感觉"切：两张卡若都要改 `app.js`，必须合并成一张
  或改为串行接力。
- 一张卡 = 一个验收标准可判定的目标；"顺便优化"类内容拆出去另开卡。
- 契约变更卡（如改 API 形状）排在所有消费方卡之前，或由主控先落地再派发。

## 冲突处理

- 合并冲突：找主控，按任务卡的 Ownership 判定保留方；不允许任何执行 agent 自行解决
  涉及他人文件的冲突。
- 发现任务卡描述与实际代码不符：停下来，更新任务卡（或换卡），再继续。

## 汇报格式（执行 agent → 主控）

```
任务卡 <id>：<一句话目标>
- 改动文件：<列表>
- 验收：<逐条对照任务卡验收标准，通过/未通过 + 证据命令输出>
- 测试：npm test 结果（tests/pass/fail）
- 遗留：<未完成项或风险，无则写"无">
```
